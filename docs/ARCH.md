# ARCH — Chroma for Hermes

## Layout

| Path | Role |
|:--|:--|
| `desktop/plugin.template.js` | SOURCE OF TRUTH for the plugin. Edit this, never the build |
| `desktop/plugin.js` | GENERATED by `scripts/regenerate.py`. Loaded by Desktop |
| `dashboard/plugin_api.py` | FastAPI `APIRouter`, mounted at `/api/plugins/chroma/` |
| `gateway-skins/` | skin YAML bundled into the package |
| `skins/` | bundled scene sources |
| `scripts/regenerate.py` | build step: template + bundled data → `desktop/plugin.js` |
| `tests/` | `node:test` suites, plus `unittest` for the backend |
| `docs/` | this documentation set |
| `install/` | install helpers |
| `rigour.yml` | quality-gate configuration (team standard; do not tune to pass) |

## Build pipeline

```
desktop/plugin.template.js  ──(scripts/regenerate.py)──▶  desktop/plugin.js
        + skins/ + gateway-skins/ + backend built-ins
```

`regenerate.py` reports its own census, e.g. "104 scenes from 140 bundled skins
+ 9 backend built-ins and 114 gateway transports". It also normalises newlines: an
earlier build doubled every CRLF, which is why the template and the build must
stay the same line count.

Rules:
- Never edit `desktop/plugin.js` — it is overwritten.
- `python scripts/regenerate.py` after EVERY template edit, then `node --check`.
- Both files are committed, so a reviewer can diff the build against the template.

## Runtime constraints

Desktop loads the plugin as plain, UNCOMPILED ESM. Only three specifiers resolve:

- `@hermes/plugin-sdk`
- `react`
- `react/jsx-runtime`

Consequences that shape the whole codebase:
- There is no `package.json`, by design, and therefore **no npm dependencies**. No
  YAML library, no plist parser, no colour library — every parser is hand-written
  and dependency-free.
- The UI is `jsx()` / `jsxs()` calls, never JSX syntax.
- React hooks must be imported explicitly; nothing is provided by a transform.

## Transport

The pane runs in the renderer and reaches the backend over JSON REST with
`ctx.rest` (exposed by the SDK as `rest(path, opts)`). There is no file-save API
on the host SDK: F3's export therefore builds a Blob in the renderer and triggers
an anchor download, which Electron's `will-download` handler routes to the user's
Downloads directory with a save dialog.

## Appearance ownership

Theme state belongs to the app's ThemeProvider. The plugin only calls the SDK —
`setTheme`, `setMode`, `previewTheme`, `clearThemePreview`:
- `previewTheme(name, mode)` repaints the ENTIRE app. Anything that calls it on
  pointer travel is a performance defect, not a debounce problem.
- Clearing a preview repaints the last committed appearance, which is what makes
  a timed preview-then-revert work.
- A preview left armed when the UI goes away strands the user on a theme they
  never chose. Ownership of the revert timer therefore sits with the picker, not
  with the individual card, so the revert still fires when a card leaves the tree.

## Storage ownership

Plugin-owned `chroma-*` keys only. The app owns `hermes-desktop-*`.

## Test architecture

Every JS suite loads the SHIPPED `desktop/plugin.js` in a VM (`tests/helpers/load-plugin.mjs`),
reads that file's own import statements, and injects stubs for exactly those names.
That design is a response to a real defect: harnesses that hand-wrote hook stubs
kept passing while the shipped build had forgotten to import `useRef` and
`useCallback`, so the page was dead on arrival in the app while every test was
green. A stub may never be added for a name the build does not import.

The harness executes function components, so component bodies really run and
handler behaviour can be asserted.

Backend tests run under the Hermes venv interpreter (FastAPI, pydantic, yaml). A
bare `python` lacks them. `tests/__init__.py` exists so the tests directory stays
a package even when a foreign `tests` package is earlier on `PYTHONPATH`.

## Backend architecture

- `APIRouter`, registered in an order that matters (see SPEC).
- Writes are atomic (`_atomic_write_text`), and a skin is written BEFORE its index
  entry, so a crash leaves an unindexed skin rather than an index pointing at
  nothing.
- Deletion moves to a trash dir; nothing is destroyed.
- Name handling is guarded (`_guard_name`, `_is_unsafe_name`) before any path is
  built.
